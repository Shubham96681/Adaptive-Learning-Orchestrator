# Adaptive Learning Orchestrator

A production-ready FastAPI application implementing a **Planner–Executor architecture** for adaptive learning assessments. This system is designed to be decoupled and LLM-ready, allowing for future integration with fine-tuned models or general-purpose LLMs without requiring a full rewrite.

## Architecture Overview

### Design Philosophy

The system follows a **decoupled, multi-stage orchestration pattern** that separates strategic decision-making (Planning) from tactical execution (Execution). This architecture provides several key benefits:

1. **Swappable Components**: The Planner and Executor are independent, allowing either to be replaced with LLM-powered implementations without affecting the other.
2. **Testability**: Each component can be tested in isolation.
3. **Scalability**: The architecture can handle additional subjects, content types, and sophisticated AI capabilities.
4. **Maintainability**: Clear separation of concerns makes the codebase easier to understand and modify.

### Architectural Components

#### 1. The Planner (`app/planners/assessment_planner.py`)

**Responsibility**: Translates high-level, potentially ambiguous user intent into a concrete, machine-readable execution plan.

**Input**:
- `StudentProfile`: Contains student ID, mastered topics, and learning goals
- `AssessmentRequest`: Contains pedagogical strategy and time constraints

**Output**: `AssessmentPlan` - A structured object containing:
- `strategy`: The pedagogical strategy to be used
- `topic_rules`: List of rules specifying which topics to select, difficulty ranges, and question counts
- `time_limit_minutes`: Total time limit for the assessment
- `reasoning_log`: Human-readable explanation of planning decisions

**Analogy**: This is the "Reasoning" (the 'R' in ReAct) or "Chain of Thought" step. It decides **what to do** and **why**.

**Key Characteristics**:
- **No database access**: The planner makes no direct queries to the problem database, keeping it pure and focused on strategy.
- **Strategy-based logic**: Implements three pedagogical strategies:
  - `REVIEW`: Focuses on mastered topics to reinforce learning
  - `NEW_TOPIC_INTRODUCTION`: Introduces new topics at appropriate difficulty levels
  - `CHALLENGE`: Mixes mastered and new topics at higher difficulty
- **Deterministic yet flexible**: Uses rule-based logic that can be easily replaced with LLM reasoning.

#### 2. The Executor (`app/executors/assessment_executor.py`)

**Responsibility**: Flawlessly executes a given `AssessmentPlan` without making strategic decisions.

**Input**: `AssessmentPlan` - The plan generated by the Planner

**Output**: `ExecutorOutput` containing:
- `selected_problems`: List of problems that match the plan's criteria
- `total_estimated_time`: Sum of estimated time for all selected problems

**Analogy**: This is the "Acting" (the 'A' in ReAct) step. It interacts with tools (the problem database) to fulfill the plan.

**Key Characteristics**:
- **No decision-making logic**: The executor is "dumb" in the sense that it doesn't make strategic choices - it only follows the plan.
- **Constraint enforcement**: Ensures selected problems fit within time limits and match topic/difficulty criteria.
- **Database interaction**: Queries the problem service to find matching problems.

### The Contract: AssessmentPlan Structure

The `AssessmentPlan` serves as the **contract** between the Planner and Executor. This structure was designed to be:

1. **Complete**: Contains all information needed for execution without requiring additional context.
2. **Structured**: Uses typed models (Pydantic) for validation and clarity.
3. **Extensible**: Can be extended with additional fields (e.g., problem types, learning objectives) without breaking existing executors.

**Structure**:
```python
{
  "strategy": "NEW_TOPIC_INTRODUCTION",
  "topic_rules": [
    {
      "topic": "Calculus",
      "difficulty_range": [1, 2],
      "question_count": 5
    }
  ],
  "time_limit_minutes": 60,
  "reasoning_log": "Detailed explanation..."
}
```

**Why this structure?**
- `topic_rules` allow the planner to specify multiple topics with different difficulty ranges, enabling complex strategies.
- `difficulty_range` as a tuple `[min, max]` provides flexibility while maintaining constraints.
- `reasoning_log` enables transparency and debugging, and is essential for LLM integration where explainability matters.
- `time_limit_minutes` ensures the executor can enforce time constraints.

### Future Extensibility

#### Plugging in a Real LLM

The architecture supports LLM integration at multiple levels:

1. **Planner Replacement**: Replace `AssessmentPlanner.generate_plan()` with an LLM call:
   ```python
   def generate_plan(self, student_profile, assessment_request):
       prompt = f"Generate an assessment plan for student {student_profile.id}..."
       llm_response = call_llm(prompt)
       return parse_llm_response_to_assessment_plan(llm_response)
   ```
   The rest of the system remains unchanged.

2. **Hybrid Approach**: Use LLM for reasoning_log generation while keeping rule-based topic selection.

3. **Executor Enhancement**: Add LLM-based problem selection criteria (e.g., "select problems that build on previous concepts").

#### Adding New Problem Types

The `Problem` model can be extended with additional fields:
- `problem_type`: "multiple_choice", "free_response", "interactive"
- `learning_objectives`: List of specific skills tested
- `prerequisites`: Topics that should be mastered first

The executor can filter by these fields without planner changes.

#### Supporting More Complex Pedagogical Strategies

New strategies can be added to the planner:
- `SPACED_REPETITION`: Based on forgetting curves
- `ADAPTIVE_DIFFICULTY`: Adjusts difficulty based on performance
- `SOCIAL_LEARNING`: Includes peer comparison problems

Each strategy generates `topic_rules` following the same contract.

### Data Access and Scaling Considerations

#### Current Implementation

- **SQLite Database**: Problems are stored in a SQLite database (`problems.db`)
- **Service Layer**: `ProblemService` abstracts data access, making it easy to swap implementations
- **Efficient Filtering**: Topic and difficulty filtering uses SQL queries with indexes for performance
- **Persistent Storage**: Data persists across server restarts

#### Scaling Bottlenecks and Solutions

1. **Memory Limitations**:
   - **Current**: All problems loaded into memory
   - **Solution**: Implement database-backed `ProblemService` with indexing on `topic` and `difficulty`
   - **Migration Path**: Change `ProblemService` implementation without modifying Planner/Executor

2. **Query Performance**:
   - **Current**: O(n) linear search through all problems
   - **Solution**: Database indexes on `(topic, difficulty)` for O(log n) queries
   - **Consideration**: For 10,000+ problems, database is essential

3. **Concurrent Access**:
   - **Current**: Single-threaded in-memory dict
   - **Solution**: Database with proper transaction handling
   - **Alternative**: Redis for high-throughput scenarios

4. **Caching Strategy**:
   - Cache frequently accessed problems by topic/difficulty
   - Use Redis for distributed caching in multi-instance deployments

#### Database Schema (SQLite)

The system uses SQLite with the following schema:

```sql
CREATE TABLE problems (
    id TEXT PRIMARY KEY,
    text TEXT NOT NULL,
    topic TEXT NOT NULL,
    difficulty INTEGER NOT NULL CHECK (difficulty >= 1 AND difficulty <= 5),
    estimated_time_to_solve_minutes INTEGER NOT NULL CHECK (estimated_time_to_solve_minutes > 0)
);

CREATE INDEX idx_topic_difficulty ON problems(topic, difficulty);
CREATE INDEX idx_topic ON problems(topic);
```

The database file (`problems.db`) is created automatically in the project root on first run.

## API Endpoints

### Assessments

#### POST `/api/assessments/generate`

Generate an assessment using the Planner-Executor architecture.

**Request Body:**
```json
{
  "student_profile": {
    "id": "student-123",
    "mastered_topics": ["Arithmetic", "Algebra"],
    "learning_goals": ["Calculus", "Geometry"]
  },
  "assessment_request": {
    "pedagogical_strategy": "NEW_TOPIC_INTRODUCTION",
    "max_total_time_minutes": 60
  }
}
```

**Response:**
```json
{
  "assessment_id": "uuid",
  "planner_output": {
    "assessment_plan": {
      "strategy": "NEW_TOPIC_INTRODUCTION",
      "topic_rules": [...],
      "time_limit_minutes": 60,
      "reasoning_log": "..."
    },
    "reasoning_log": "..."
  },
  "executor_output": {
    "selected_problems": [...],
    "total_estimated_time": 45
  },
  "created_at": "2024-01-01T00:00:00"
}
```

**Pedagogical Strategies:**
- `REVIEW`: Focus on mastered topics to reinforce learning
- `NEW_TOPIC_INTRODUCTION`: Introduce new topics at appropriate difficulty
- `CHALLENGE`: Mix topics at higher difficulty levels

## Design Decisions

### 1. Planner-Executor Separation

**Decision**: Strict separation between planning and execution.

**Rationale**: 
- Enables independent testing and development
- Allows LLM integration at either layer
- Makes the system more maintainable

### 2. AssessmentPlan as Contract

**Decision**: Use a structured, typed model (`AssessmentPlan`) as the contract.

**Rationale**:
- Provides clear interface between components
- Enables validation and type safety
- Makes the contract explicit and documented

### 3. In-Memory Storage (Current)

**Decision**: Start with in-memory dictionary storage.

**Rationale**:
- Simplifies initial implementation
- Easy to replace with database later
- Service layer abstraction makes migration straightforward

### 4. Pydantic Models

**Decision**: Use Pydantic for all data models.

**Rationale**:
- Automatic validation
- Type safety
- JSON schema generation for API docs
- Easy serialization/deserialization

### 5. UUID for IDs

**Decision**: Use UUID for all entity IDs.

**Rationale**:
- Globally unique identifiers
- Security (non-sequential, harder to guess)
- No collision risk in distributed systems
